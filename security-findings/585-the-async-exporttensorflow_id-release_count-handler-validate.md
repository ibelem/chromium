# Security finding #585: The async `ExportTensor(flow_id, release_count)` handler validates …

**Summary:** The async `ExportTensor(flow_id, release_count)` handler validates …

**CWE IDs:** CWE-367: Time-of-check Time-of-use (TOCTOU) Race Condition / CWE-20: Improper Input Validation
**Severity / Impact:** A compromised renderer can invoke the non-blocking async `ExportTensor` regardless of feature state. Unlike `ExportTensorSync`, it does not block the renderer until the release SyncToken is actually registered with the sync-point manager. When SyncPointGraphValidation is disabled, WebGPU's wait on the renderer-supplied `release` token can be satisfied before the export task (which ends WebNN's exclusive `representation_access_` via ExportTensorImpl, line 199, and performs device synchronization) has run, letting WebGPU access/write the shared-image tensor memory while WebNN is still finishing a prior read on it — a cross-process data race on GPU tensor memory (potential memory corruption / info leak). The service, not the (untrusted) renderer, must enforce the documented invariant.
**Affected location:** `targets/chromium/services/webnn/webnn_tensor_impl.cc:164` — `WebNNTensorImpl::ExportTensor()`
**Validated for repos:** chromiumWebnn
**Trust boundary:** renderer ↔ WebNN service Mojo (WebNNTensor associated pipe)

## Description / Root cause
The async `ExportTensor(flow_id, release_count)` handler validates only the `kWebGpuInterop` usage flag (167) and the presence of `gpu_task_scheduler()` (172). It then unconditionally builds the release SyncToken (178-182) and schedules the export task (184-203). There is NO check that the `SyncPointGraphValidation` feature is enabled, even though webnn_tensor.mojom:69-71 states this async entrypoint 'should not be called if SyncPointGraphValidation is disabled' precisely because Mojo/SyncToken ordering cannot otherwise be guaranteed, and a blocking `[Sync] ExportTensorSync` (206-) exists as the mandatory fallback for that case.

**Validator analysis:** The missing check is real and reachable: WebNNTensorImpl::ExportTensor (webnn_tensor_impl.cc:164-204) is an ordinary (non-[Sync]) Mojo method on the WebNNTensor associated pipe that a compromised renderer can invoke at will. It performs no SyncPointGraphValidation feature gate, even though webnn_tensor.mojom:69-71 documents it 'should not be called if SyncPointGraphValidation is disabled' and mojom:75-80 explains the [Sync] ExportTensorSync exists precisely so SyncToken registration completes before the token is handed to WebGPU. Unlike ExportTensorSync (206-250, which blocks the renderer via the =>() reply), the async path returns without confirming the release token is registered with the sync-point manager, so when the feature is disabled (the TODO at mojom:75 confirms this is a current, real deployment state) a renderer can pass release token N to a WebGPU wait on a separate pipe before the export task registers/releases it, letting WebGPU begin shared-image access before ExportTensorImpl (line 199) ends WebNN's representation_access_. The vulnType is best framed as CWE-20 (missing service-side enforcement of a documented invariant) more than classic CWE-367; the memory-corruption/info-leak impact is plausible but partly speculative since shared-image BeginAccess/EndAccess offers some coordination — the concrete, provable defect is the unenforced feature gate leaving a cross-process release-token race open. The proposed fix is correct and sufficient in direction: at the top of ExportTensor, if features::kSyncPointGraphValidation is not enabled, call ReportBadMessage(kBadMessageInvalidTensor) and return (or only bind the async method when the feature is on), forcing the ExportTensorSync fallback; this mirrors the existing bad-message guards at 167-175 and does not rely on renderer cooperation.

## Exploit / Proof of Concept
Compromised renderer with the SyncPointGraphValidation feature disabled: create a kWebGpuInterop tensor, run a graph Dispatch that reads/writes it, then send async `ExportTensor(flow_id, release_count=N)` over the WebNNTensor pipe and immediately instruct WebGPU to wait on release token N and begin writing the shared image. Because `ExportTensor` returns without confirming release registration and no feature gate rejects the call, WebGPU's wait can resolve before ExportTensorImpl relinquishes WebNN access, producing concurrent WebNN/WebGPU access to the same tensor. Note: the intra-service is_exported() gate in webnn_graph_impl.cc:82-100 and the single scheduler sequence do serialize the WebNN Dispatch/Import/Export tasks and close the WebNN-internal window; the unclosed window is the cross-process release-token race that SyncPointGraphValidation+ExportTensorSync were designed to prevent, which this handler leaves open.

## Suggested fix
Gate the async path on the feature at the service trust boundary: at the top of `WebNNTensorImpl::ExportTensor`, if the SyncPointGraphValidation feature (the same flag gpu uses, e.g. features::kSyncPointGraphValidation) is not enabled, call `GetMojoReceiver().ReportBadMessage(kBadMessageInvalidTensor)` and return, forcing renderers to use the `[Sync] ExportTensorSync` fallback. Equivalently, only expose/accept the async `ExportTensor` method when the feature is on. Do not rely on the renderer honoring the mojom comment.
